# План обучения: DevOps за 8 лабораторных

План рассчитан на самообучение в терминале на своём сервере. Темп: 1–2 лабораторные
в неделю, каждая занимает 1,5–3 часа чистого времени в терминале.

Принципы курса:

- **Только практика.** Каждая лабораторная — это набор действий в терминале и чек-лист «готово».
- **Порядок важен.** Каждая лабораторная опирается на результаты предыдущей.
- **Контрольные вопросы обязательны.** Можно отвечать устно/себе, но формулировать
  ответы вслух — лучший способ закрепить материал.
- **Референсные решения** есть, но открывать их можно только после собственной попытки.

## Секция 0. Подготовка окружения (предварительная, ~30 минут)

Проверь, что на сервере есть и работает:

```bash
# 1. Доступ по SSH уже есть (ты на сервере)
# 2. git
git --version
# 3. Docker Engine 24+
docker --version
# 4. curl
curl --version
# 5. Docker реально запускает контейнеры
docker run --rm hello-world
```

### Если Docker не установлен (Ubuntu 22.04 / 24.04)

Официальный способ от Docker Inc.:

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl

sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
  https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# Чтобы не писать sudo перед docker (перелогинься после):
sudo usermod -aG docker "$USER"
```

Проверка: `docker compose version` и `docker run --rm hello-world`.

Критерий готовности секции 0: все пять команд выше отработали успешно.

## Лабораторная 001. Первый Dockerfile ✅

**Цель:** написать Dockerfile для простого Flask-приложения, собрать образ на сервере,
запустить контейнер и убедиться, что приложение отвечает.

**Задания (пошагово — в README лабораторной):**

1. Написать `Dockerfile` в каталоге лабораторной (FROM, WORKDIR, COPY, RUN, EXPOSE, CMD).
2. Собрать образ: `docker build -t lab01:0.1 .`
3. Запустить контейнер: `docker run --rm -d -p 8000:8000 lab01:0.1`
4. Проверить эндпоинты `/` и `/health` через curl.
5. Осмотреть артефакты: `docker images`, `docker ps`, `docker logs`, `docker inspect`, `docker history`.
6. Бонусы: кэширование слоёв, non-root пользователь, HEALTHCHECK, gunicorn.

**Чему научишься:**

- разница «образ / контейнер / реестр»;
- контекст сборки и для чего `.dockerignore`;
- слои и кэш сборки — почему порядок команд в Dockerfile важен;
- что делает `EXPOSE` и почему без `-p` снаружи приложения не видно;
- `CMD` vs `ENTRYPOINT`.

**Критерий готовности:**

- [ ] Образ `lab01:0.1` собран без ошибок
- [ ] Контейнер запущен, `curl http://localhost:8000/` и `/health` возвращают JSON
- [ ] Ты можешь показать и объяснить вывод `docker history lab01:0.1`
- [ ] Отвечены контрольные вопросы из README лабораторной

**Время:** 1,5–2,5 часа.

## Лабораторная 002. Лучшие практики Dockerfile ✅

**Цель:** «доточить» образ из лабы 001 до приличного состояния.

**Задания:**

1. Замерить размер образа из лабы 001 (`docker images`).
2. Уменьшить его: базовый образ `*-slim`/`alpine`, `pip --no-cache-dir`, правильные ENV для Python.
3. Запустить приложение от non-root пользователя (`USER`).
4. Добавить `HEALTHCHECK` и убедиться, что `docker inspect` показывает статус `healthy`.
5. Написать многоэтапную сборку (multi-stage) хотя бы на примере «архива с кодом».
6. Замерить размер нового образа и зафиксировать разницу.

**Критерий готовности:**

- [ ] Новый образ заметно меньше прежнего (размеры записаны в заметки)
- [ ] `docker exec` показывает, что процесс не root
- [ ] Healthcheck работает: статус `healthy`
- [ ] PEP/бест-пракติกс: образ проходит по пунктам checklist'а Docker (краткий конспект у тебя есть)

**Время:** 2–3 часа.

## Лабораторная 003. Docker Compose 🚧

**Цель:** запускать мультисервисный проект одной командой.

**Задания:**

1. Написать `docker-compose.yml`: Flask-приложение (из лабы 001) + Nginx как reverse-proxy.
2. Поднять: `docker compose up -d`. Проверить: `docker compose ps`, `docker compose logs -f`.
3. Настроить сеть: приложение доступно только внутри сети, наружу торчит только nginx (порт 80).
4. Добавить номенатурный том: например, данные/логи, которые переживут `docker compose down`.
5. Разобраться с `profiles`, переменными окружения (`.env`) в compose-файле.

**Критерий готовности:**

- [ ] `docker compose up -d` поднимает оба сервиса
- [ ] Приложение доступно через nginx на 80-м порту
- [ ] Приложение недоступно снаружи по 8000-му порту (только nginx)
- [ ] Данные из тома сохранились после `down` / `up`

**Время:** 2–3 часа.

## Лабораторная 004. Регистры и отладка 🚧

**Цель:** хранить образы в регистре и уметь отлаживать «сломанный» контейнер.

**Задания:**

1. Создать доступ к GHCR (GitHub Container Registry) через токен; `docker login`.
2. Протегировать и запушить образ: `docker tag` + `docker push`.
3. Установить на чистой машине/контейнере: `docker pull` и `docker run`.
4. Отладочный полигон: три намеренных поломки (неверный порт, неверный путь в COPY,
   зависший процесс) — найти каждую по `docker logs`, `docker exec -it --user root <ctr> sh`,
   `docker inspect`, `docker stats`.

**Критерий готовности:**

- [ ] Образ доступен в GHCR и запускается с чистой машины
- [ ] Все три поломки найдены и объяснены (что видел в логах, какой вывод тебя привёл к ответу)

**Время:** 2–3 часа.

## Лабораторная 005. CI: GitHub Actions 🚧

**Цель:** каждый push в ветку должен собирать образ в CI.

**Задания:**

1. Написать workflow `.github/workflows/build.yml`: checkout → login-action (секреты репозитория) → build-push-action.
2. Создать GitHub-секреты (токены) — и убедиться, что они НЕ видны в коде и логах.
3. Намеренно сломать сборку (ошибка в Dockerfile) и прочитать, как CI отобразил проблему.
4. Добавить кэш слоёв сборки (`cache-from`/`cache-to`).

**Критерий готовности:**

- [ ] Грин-ран на текущей ветке, лог джобы содержит успешный сборку (и/или push)
- [ ] Логи не содержат секретов
- [ ] Повторный билд заметно быстрее за счёт кэша

**Время:** 2–3 часа.

## Лабораторная 006. CD: деплой на VPS 🚧

**Цель:** после push обновлённое приложение само заводится на сервере.

**Задания:**

1. Подготовить на сервере compose-проект из лабы 003 (обрацы из GHCR).
2. Написать deploy-workflow: push в `main` → CI собирается → deploy джоба через ssh-action.
3. Передавать SSH-ключ как deployment secret; проверить права на сервере (малые привилегии).
4. Добавить healthcheck после деплоя: workflow падает, если `/health` не отвечает.
5. Написать `.env`/секреты для продакшена — ничего чувствительного в образе и в git.

**Критерий готовности:**

- [ ] Изменил строку в `app.py` → push → через пару минут изменение видно на сервере без SSH
- [ ] Деплой, который уронил приложение, завершается ошибкой и не оставляет сервер в «половине»

**Время:** 2–3 часа.

## Лабораторная 007. Безопасность 🚧

**Цель:** увидеть типовые уязвимости в образе и закрыть их.

**Задания:**

1. Установить/подключить Trivy (`trivy image lab01`) — прочитать отчёт, понять уровни (CRITICAL/HIGH/MEDIUM/LOW).
2. Закрыть (или осознанно игнорировать) найденные findings: обновить зависимости, обновить базовый образ,
   `apt-get` с удалением кэша в одном слое.
3. Аудит: кто запускает процесс? Какие секреты есть в слое (`docker history`)?
4. Зафиксировать «политику»: какие findings блокируют деплой, а какие — нет.
5. Запустить trivy в CI (lab 005 workflow) с порогом.

**Критерий готовности:**

- [ ] `trivy image` не показывает CRITICAL/HIGH в твоём образе (или у тебя есть обоснованный список исключений)
- [ ] Процесс работает non-root
- [ ] В слое сборки/образа нет секретов (проверено по history)

**Время:** 2–3 часа.

## Лабораторная 008. Финальный проект 🚧

**Цель:** задеплоить маленький проект «под ключ»: приложение + БД, с CI и CD, на чистом сервере.

**Задания:**

1. Расширить Flask-приложение: хранение данных (SQLite или Postgres) — например, «заметки»: POST/GET.
2. Написать compose: app + db (+ nginx, как в лабе 003), с бэкапом данных (том).
3. CI: сборка + тесты (хотя бы smoke-тест на `/health`) + trivy (lab 007).
4. CD: деплой на VPS (lab 006) + откат на предыдущий тег одной командой.
5. Написать мини-«операционную» документацию в README проекта: как обновить, как откатить,
   как смотреть логи, как восстановить БД.

**Критерий готовности:**

- [ ] Чистый клон репозитория + чистый сервер → проект запущен минимальным числом ручных команд
- [ ] Откат на предыдущую версию работает
- [ ] Документация позволяет «новому сисадмину» (другу) поднять проект по твоим запискам

**Время:** 4–6 часов (можно разбить на несколько сессий).
